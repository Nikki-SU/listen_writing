# 如何与 AI 讨论（本项目）

> 目的：把「怎么讨论」固定下来，减少来回返工。每一条都来自我们已经发生的对话；不对的地方直接改本文件。

## 1. 先对齐「做什么」，再谈「怎么做」

- 先说清楚：给谁用、解决什么问题、什么算做完（验收标准）。
- 世界观没对齐之前，不要先写代码、先选技术栈。
- 「你先去查一查」的意思是：先给有依据的方案对比，不要直接动手改架构。

## 2. 一次只问一件事，先总后分

- 人一次能同时判断的决策有限。先给全貌（3–5 条），再逐条确认。
- 不要一次抛 10 个互相影响的约束；漏掉一条，后面就会返工。

## 3. 描述问题用四段式

1. **现象**：看到了什么（截图 / 版本 / 哪一句 / 哪个按钮 / 哪一步）。
2. **期望**：正确应该是什么样。
3. **约束**：不能牺牲什么（例：语气词不能删、单句播放必须精准、版本号必须对应改动）。
4. **验收**：怎么算改好了（点哪里、看到什么、构建/部署是否通过）。

## 4. 直接指出「你理解错了」

- 不要用模糊的否定。直接说：你理解错了，我要的是 X，不是 Y。
- 给了反例时，以反例为准；不要用「通常 / 最佳实践」把反例压过去。

## 5. 决策人拍板，AI 给依据

- 架构 / 技术选型：给 2–3 个选项 + 推荐 + 理由 + 代价，不要只丢一个结论。
- 涉及外部系统（DSH、模型、库）：先查文档 / 源码 / 实测，再下结论，并给出链接。
- 不确定的事明确说「不确定」，不要编。

## 6. 改代码的边界

- 改之前说清楚：动哪些文件、会不会改数据结构 / 接口 / 版本号。
- 改完必须能验收：类型检查、构建、接口 E2E、部署核对；不能只看「代码写完了」。
- 约定文件（`API_CONTRACT.md` / `TODO.md` / `DEPENDENCIES.md`）随改动同步。

## 7. 已知偏好（可随时补充）

- 默认用图标，不默认写文字；只有含义不通用时才用文字。
- 布局尽量稳定：开不开 AI 模式、切不切页面，不要出现无意义的跳动。
- 精准优先：单句播放只播那一句；停止任务要保留已完成结果。
- 原始数据优先：访谈的语气词、停顿、重复不为「好看」而删。
- 少打扰：纯前端更新不重启后端；但每次改动都要 bump 版本号，版本号与改动一一对应。
- 不想让团队成员本地起后端：优先「DSH 工作区 + 插件分发」，只装 DSH 和插件即可用。
- 不用弹窗替代本该在页面里完成的操作；不做糊弄式实现。

## 8. 讨论模板（可直接复制）

```text
背景：
现象 / 问题：
期望：
约束（不能牺牲的）：
验收标准：
我倾向的方案（可选）：
```

## 9. AI 在讨论中的义务

- **先复述**：动手前用一两句话复述目标，方便你立刻发现偏差。
- **先证据后结论**：外部系统 / 库的行为要给出文档或实测依据。
- **失败要说**：构建 / 部署 / 测试失败不隐瞒，修到跑通再汇报。
- **区分「已做」和「计划做」**：不把计划说成已完成。
